# 情报日报双定时与每日幂等投递设计

## 背景与目标

现有工作流使用 `0 0 * * *`，对应北京时间 08:00。GitHub 官方说明整点属于
Actions 高负载时段，scheduled run 可能延迟，负载过高时甚至可能被丢弃。
2026-08-05 的工作流保持 active、默认分支仍为 `main`，但 GitHub 未创建当天的
scheduled run，因此采集与钉钉投递均未开始。

目标是在不修改 Secrets、不降低情报核实标准的前提下，让日报通常在北京时间
08:00 前后送达，并用第二次定时机会弥补 GitHub 丢失一次 cron 事件的情况，同时
避免同一天重复发送正式日报。

## 方案比较

1. 单次 07:50 定时：改动最小，也避开整点，但该 cron 仍可能被 GitHub 丢弃。
2. 07:50 主任务 + 08:20 兜底，不做幂等：可靠性提高，但主任务延迟时可能发送两份。
3. 07:50 主任务 + 08:20 兜底 + 当天正式投递幂等：兼顾可靠性与去重，是本次采用方案。

外部云调度器可提供更强 SLA，但会引入新的账号、凭据和运维面，本次不采用。

## 触发与运行标识

- 主 cron：`50 23 * * *`，即北京时间每天 07:50。
- 兜底 cron：`20 0 * * *`，即北京时间每天 08:20。
- scheduled run 使用可识别的 `scheduled-live` 运行标题。
- 手动 `dingtalk_live` 使用 `manual-live` 运行标题。
- 手动 `dry_run` 和 `dingtalk_test` 保持独立标识，不参与正式投递幂等判断。
- 两个 cron 均继续固定使用 `daily + 12 + dingtalk_live`，查询基础预算 12、弹性 3、
  总硬上限 15 不变。

## 每日幂等门禁

工作流在安装依赖和采集前执行只读预检：

1. 使用当前仓库自动提供的 `GITHUB_TOKEN` 和 `actions: read` 权限查询本工作流运行历史。
2. 按北京时间自然日筛选当前运行以外的成功运行。
3. 只有标题明确为 `scheduled-live` 或 `manual-live` 的运行才视为当天正式投递；
   `dry_run`、测试投递和旧版本运行不阻塞。
4. 若当天已有成功正式投递，本次运行写明跳过原因并停止后续采集、AI、博查和钉钉步骤。
5. 若没有成功正式投递，继续正常采集和投递。
6. API 查询采用有限重试；连续失败时令预检失败，不以“可能重复发送”为代价放行。

现有 `concurrency: laser-space-daily` 保持不变，因此主任务、兜底任务和手动任务不会
并发发送。第一项任务完成后，排队的下一项任务会重新执行幂等预检。

## 失败语义

- 主任务没有被 GitHub 创建：08:20 兜底仍有独立触发机会。
- 主任务运行失败或钉钉拒绝：其结论不是成功，兜底可以再次尝试。
- 主任务投递成功：兜底运行快速跳过，不重复采集或发送。
- 预检 API 不可用：工作流失败并保留明确诊断，不冒险重复推送。
- Actions 成功仍不替代情报业务质量判断；正式投递成功继续以通知器收到钉钉
  `errcode=0`、CLI 写入 `delivery-status.json=accepted` 为准。

## 测试与验收

- 静态测试验证两个 UTC cron、默认手动 `dry_run`、scheduled 固定 `dingtalk_live`、
  `actions: read` 和幂等预检均存在。
- 单元测试覆盖北京时间日期边界、正式/非正式运行识别、排除当前运行、成功跳过、
  前次失败允许重试以及 API 失败时拒绝放行。
- 完整离线测试必须全部通过，`git diff --check` 必须通过。
- 合并后手动执行一次今天的 `dingtalk_live`；运行标题必须是 `manual-live`，报告日期
  属于当前运行，钉钉返回成功后才宣称补发完成。
- 次日核对 07:50 或 08:20 至少产生一个 scheduled run；若两者都创建，第二个必须
  在幂等门禁处跳过且不再发送。

## 安全边界

- 不读取、输出或修改现有 Secret 值。
- 不修改仓库可见性，不暂停 workflow，不降低来源和严格核实规则。
- 不用旧日报冒充当前日报，不把候选线索标为已核实。
- 手动 `dry_run` 仍是默认值；只有显式 `dingtalk_live` 和两个 cron 允许正式投递。
