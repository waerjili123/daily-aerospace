# 每日 08:00 生产推送设计

日期：2026-08-04  
状态：待书面确认后实施  
目标分支：`codex/verification-promotion-20260728`（PR #6）

## 1. 背景与目标

当前高质量版本只存在于 PR #6 分支，默认分支 `main` 仍是旧的 4 次查询、仅 `dry_run` 工作流。GitHub Actions 的 `schedule` 只执行默认分支上的 workflow，因此仅在 PR 分支添加 cron 不会形成真实定时推送。

本次目标是：

- 每天北京时间 08:00 启动当前高质量采集流程；
- 日常使用 12 次基础查询，遇到不确定事件时最多追加 3 次，总上限 15 次；
- 采集结束后自动发送不带“【测试】”标识的钉钉正式日报；
- 没有严格已核实信息时仍如实发送高可信待核实、候选线索或“暂无重要新增”，不把“无严格已核实”当作生产故障；
- 真实采集失败时发送降级快报或异常告警，Actions 仍如实标红；
- 手动运行默认继续为 `dry_run`，测试发送继续保留严格门槛。

“08:00”表示 GitHub 在北京时间 08:00 计划启动任务，不承诺 08:00 整收到消息。正常情况下消息将在采集完成后的约 5–15 分钟内到达；GitHub 排队或外部网站超时可能造成进一步延迟。

## 2. 方案比较

### 方案 A：当前工作流增加生产模式并合并到 `main`（采用）

- 在同一 workflow 中支持手动 dry-run、严格测试发送和定时正式发送。
- PR #6 测试通过后合并到 `main`，让 GitHub 原生 schedule 生效。
- 优点：结构最简单，复用已经验收的采集和降级链路，运行记录集中。
- 风险：采集耗时会直接影响实际送达时间；通过明确说明“08:00 启动”接受该风险。

### 方案 B：保持 PR 不合并，仅每天手动触发

- 不改变默认分支。
- 无法形成无人值守的每天 08:00 推送，不满足目标。

### 方案 C：提前采集、08:00 单独发送

- 例如 07:40 生成快照，08:00 只发送。
- 可提高准点送达能力，但需要持久化跨 workflow 产物和过期快照保护，复杂度明显更高。
- 当前目标是“08:00 开始推送”，本阶段不采用。

## 3. 工作流设计

### 3.1 触发方式

保留 `workflow_dispatch`，新增：

```yaml
schedule:
  - cron: "0 0 * * *"
```

GitHub cron 使用 UTC，`00:00 UTC` 对应北京时间 `08:00`。

### 3.2 三种投递模式

- `dry_run`：默认手动模式，只生成报告和诊断，不调用钉钉。
- `dingtalk_test`：手动测试模式，标题带“【测试】”；必须满足至少 1 条本轮严格已核实信息及分类内容门槛，否则失败且不发送。
- `dingtalk_live`：正式生产模式，标题不带测试标识；发送本轮如实生成的正式报告，不要求每天必须出现严格已核实事件。

定时事件固定映射为：

- `discovery_mode=daily`
- `max_queries=12`
- `delivery_mode=dingtalk_live`

手动事件继续读取用户选择，默认仍为 `daily + 12 + dry_run`。

### 3.3 Secrets 使用

- 仅 `dingtalk_test` 和 `dingtalk_live` 注入仓库现有的 `DINGTALK_WEBHOOK` 与 `DINGTALK_SECRET`。
- `dry_run` 使用无效占位值，避免误发。
- 不读取、不显示、不修改 Secret 值。

### 3.4 分支保护

现有仅允许 `codex/verification-promotion-20260728` 的临时 guard 将调整为仅允许：

- PR 验证阶段的当前分支；
- 合并后的 `main`。

这样 PR 中仍能安全 dry-run，合并后定时任务不会被旧 guard 阻断。

## 4. 投递与失败语义

### 正常生产运行

1. 执行发现、正文抓取、结构化、核实、去重和短报渲染。
2. 报告可以包含严格已核实、高可信待核实和候选线索，但状态不得混淆。
3. 调用钉钉机器人。
4. 只有钉钉返回整数 `errcode=0` 才写入 `delivery-status.json: accepted` 并以成功结束。

### 失败运行

- 已产生候选快照：发送“【降级】情报快报”，包含本轮可追溯线索和失败阶段。
- 尚未产生候选快照：发送“【异常】运行告警”，不伪造情报。
- 降级快报或告警送达后，原始采集故障仍使 Actions 标红，避免把“通知送达”误认为“业务成功”。
- 钉钉拒绝或网络失败：Actions 标红，投递状态为 `failed`。

`dingtalk_test` 的“至少 1 条严格已核实”门槛只用于测试验收，不应用于每日生产发送。Actions #48 正是因为该测试门槛而未发送，不能将这一规则直接用于定时生产。

## 5. 报告呈现

- 正式标题：`中国激光与商业航天情报日报｜YYYY-MM-DD`。
- 融资新闻与招标采购继续硬性分区。
- 每条信息保留日期、主体、事件、明确金额或规模、可信状态和来源链接。
- 同一事件只展示一次。
- 没有严格已核实信息时仍可展示清楚标注的高可信待核实和候选线索；所有板块均无实质内容时发送简短的“暂无重要新增”日报，而不是伪造内容。

- 若首次正式运行异常，提交一个仅移除 `schedule` 的修复，先停止后续自动触发，不删除历史和产物。
- `first-version` 标签继续保留，不移动、不覆盖。
- 不修改 Secrets 和仓库可见性。
- 不降低严格已核实标准；只把测试发送门槛与每日生产投递规则分开。
- PR #6 只在上述测试通过后合并。

## 8. 验收标准

- `main` 上的 workflow 每天北京时间 08:00 计划触发。
- 定时运行使用当前高质量采集链路，查询总上限 15。
- 正式日报无“【测试】”标识。
- 无严格已核实信息时不因测试门槛失败，并且不把候选冒充已核实。
- 所有展示信息均可追溯；融资与招标不混淆；同事件不重复。
- 钉钉 `errcode=0` 才判定送达成功。
- 手动默认保持 `dry_run`。
