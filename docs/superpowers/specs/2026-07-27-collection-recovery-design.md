# 情报采集链路恢复设计

日期：2026-07-27

## 目标与优先级

当前最高优先级是恢复真实信息采集，而不是优化内容质量。首轮验收只证明以下链路成立：

1. 博查 HTTP 200 响应中的 `data.webPages.value` 能被解析。
2. 至少产生一条真实候选信息。
3. 候选保留可访问的原始来源链接。
4. 整个验收保持 `dry_run=true`，不发送钉钉。

分类准确度、跨阶段串联、去重质量、官方来源覆盖和北京时间 07:30 调度均在采集恢复后处理。

## 已选方案

采用“仅手动、小规模验收”方案：

- 日报 workflow 在修复期间保持停用。
- 先将 PR #3 的博查包装响应修复更新到最新 `main`。
- 工作流暂时移除 `schedule` 入口，只保留 `workflow_dispatch`。
- 手动验收增加查询数量输入，默认值保持安全；首次仅执行 4 个核心分类查询。
- 手动验收强制 `dry_run=true`，不允许该阶段发送钉钉。
- Artifact 人工审核通过前，不恢复定时任务。

不采用以下方案：

- 临时启用现有定时 workflow：存在验收窗口内再次自动推送空日报的风险。
- 直接执行完整查询：当前空状态约产生 15 次博查调用，没有必要先消耗完整额度。

## 数据流

```text
4 个核心分类查询
  → 博查 Web Search API
  → 解析 data.webPages.value
  → Candidate 列表
  → 原始网页抓取
  → 分析与核验
  → Markdown + data 状态
  → Artifact
```

本阶段以 `Candidate` 列表非空作为采集成功的第一门槛。后续网页无法抓取、分析降级或核验失败必须在报告和指标中明确呈现，不能把“无法核验”写成“没有信息”。

## 实现边界

### 博查解析

复用 PR #3 的实现：

- 兼容根级 `webPages.value`。
- 兼容真实响应 `data.webPages.value`。
- 检查 HTTP 200 内的业务 `code`。
- 对鉴权、限额、服务端和异常响应返回脱敏的受控错误。

### 手动验收模式

工作流在验收阶段：

- 不包含 `schedule` 触发器。
- 只允许 `workflow_dispatch`。
- `dry_run` 固定为安全模式，不能通过输入关闭。
- 提供小规模查询上限，首次设为 4。
- 仍上传 `reports/` 和 `data/` Artifact。
- 不把验收产物自动提交到 `main`。

### 暂不处理

- 不运行 `dry_run=false`。
- 不发送钉钉。
- 不更改 Secrets。
- 不恢复定时触发。
- 不修改仓库可见性。
- 不为内容质量进行大范围重构。

## 错误处理与可观测性

Artifact 和日报必须能区分：

- 博查请求失败。
- 博查响应解析失败。
- 博查返回成功但候选为 0。
- 候选存在但网页抓取失败。
- 候选存在但分析或核验降级。

Actions 的进程成功不能单独作为业务成功标准。

## 测试与验收

实施后依次验证：

1. PR #3 相关单元测试通过。
2. 完整离线测试通过。
3. workflow 配置测试证明没有定时入口、不能发送钉钉且查询数受限。
4. 手动运行一次 `dry_run=true`。
5. 下载 Artifact 并确认：
   - 不再出现“博查 API 返回格式异常”；
   - 博查候选数大于 0；
   - 至少一条候选带真实原始链接；
   - 抓取、分析或核验失败被如实标记。

只有以上条件通过，才进入内容质量和北京时间 07:30 调度修复。
