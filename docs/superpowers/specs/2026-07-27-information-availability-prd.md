# 激光与商业航天日报“有无信息”修复 PRD

- 日期：2026-07-27
- 状态：待用户评审
- 优先级：P0
- 适用仓库：`waerjili123/daily-aerospace`
- 关联变更：PR #4 `fix: surface pending collection candidates`（当前未合并）

## 1. 背景

2026-07-25、2026-07-26 的定时任务虽然显示 Actions 成功，但日报没有可用情报。后续核对确认：

- 博查真实搜索结果位于 `data.webPages.value`；
- 修复解析后，4 个核心查询能够返回 39 条候选；
- 候选中包含 2022、2023 年旧闻，以及激光打印机、激光美容防护眼镜、通用 AI 算法等明显无关内容；
- 部分候选的原网页存在人机验证、TLS 证书链或 HTTP 521 问题，导致正文无法抓取；
- 原系统把正文抓取失败等同于“没有信息”，使用户看不到已经获得的标题、摘要和链接；
- 现有请求使用 `freshness=noLimit`，且四条核心查询范围过宽；
- `discovered_at` 表示系统发现时间，不能替代来源发布日期。

本 PRD 只解决第一优先级问题：让日报稳定呈现可读、近期、主题相关的候选信息。正文核验率、定时调度和钉钉正式发送不在本阶段恢复。

## 2. 产品目标

一次受控的 4 查询手动采集应当：

1. 最终展示至少 5 条候选信息；
2. 优先展示来源发布日期位于最近 7 天的候选；
3. 每条候选至少包含标题、摘要和原始链接；
4. 不出现激光打印机、激光雕刻、激光美容、通用医疗或无关通用 AI 等明显噪声；
5. 正文抓取失败时仍展示搜索结果，并明确标注“未核实”及失败原因；
6. 通过采集漏斗指标区分“程序运行成功”和“业务采集成功”。

## 3. 非目标

本阶段不处理：

- 不合并 PR #4；
- 不恢复或修改 `schedule`；
- 不执行 `dry_run=false`；
- 不发送钉钉；
- 不修改 Secrets；
- 不修改仓库可见性；
- 不暂停或启用 workflow；
- 不通过关闭 TLS 校验绕过证书错误；
- 不保证每条候选完成正文核验；
- 不优化三个月趋势、项目串联或融资主体去重；
- 不以大模型二次分类作为候选进入日报的必要条件。

## 4. 用户与核心场景

### 4.1 主要用户

日报接收者需要在每天的报告中快速判断：

- 今天是否出现新的激光与商业航天相关信息；
- 信息属于哪个板块；
- 信息是否已经核实；
- 原始来源在哪里；
- 为什么某条信息暂时无法完成核验。

### 4.2 核心场景

当博查已返回相关搜索结果，但原网页无法抓取时，系统仍应把标题、发布日期、搜索摘要和链接交付给用户，而不是显示“暂无已核实信息”后结束。

## 5. 信息板块

本阶段保留四个核心板块，每个板块使用独立查询语义：

1. **激光通信**
   - 主题锚点：激光通信、空间激光通信、星间激光通信、激光通信终端、光通信终端；
   - 事件锚点：采购、招标、中标、结果、变更、延期、终止。
2. **激光武器/反无人机**
   - 主题锚点：激光武器、高能激光、定向能激光、激光反无人机、激光反制；
   - 事件锚点：采购、招标、中标、结果、变更、延期、终止。
3. **光电转塔/吊舱**
   - 主题锚点：光电转塔、光电吊舱、机载光电、舰载光电、无人机光电载荷；
   - 事件锚点：采购、招标、中标、结果、变更、延期、终止。
4. **商业航天融资**
   - 主体锚点：商业航天、运载火箭、卫星公司、卫星制造、卫星运营；
   - 事件锚点：融资、股权投资、战略投资、增资、天使轮、种子轮、Pre-A 轮、A 轮、B 轮及后续轮次；
   - 不再混入采购、招标、中标等采购事件词。

所有查询继续限定中国境内语义。一次验收运行只执行以上 4 个核心查询。

## 6. 数据流

```text
4 个分类查询
  → 博查 Web Search API（近一个月）
  → 解析 data.webPages.value
  → 保存来源发布日期 datePublished
  → 标题/摘要相关性门槛
  → 时间分桶与候选补足
  → URL 去重
  → 正文抓取、分析、核验
      ├─ 成功：进入已核实事件
      └─ 失败：进入未核实候选
  → Markdown 报告 + 采集漏斗指标
  → Artifact（dry-run，不发送钉钉）
```

## 7. 功能需求

### FR-1：博查请求时效范围

- 4 个核心查询使用博查支持的近一个月时效范围，不再使用 `noLimit`。
- 实施时必须用受控测试确认对应参数值被博查接受。
- 如果博查拒绝该时效参数，运行应记录明确的业务失败原因，不得静默回退到 `noLimit`。
- `summary=true`，每个查询的返回上限保持 10 条。

### FR-2：解析来源发布日期

- 从 `data.webPages.value[*].datePublished` 读取来源发布日期。
- 日期必须解析为带时区的时间；缺少时区时按保守规则标记为“日期不可确定”，不得自行假定为北京时间。
- `discovered_at` 继续表示系统发现时间。
- 来源发布日期必须使用独立字段保存，不得用 `discovered_at` 覆盖。
- 未来日期超过本次运行结束时间 24 小时的结果视为日期异常，不进入最终候选。

### FR-3：候选相关性门槛

在正文抓取之前，基于规范化后的 `title + summary + snippet` 执行确定性过滤：

- 非融资板块必须命中至少一个对应主题锚点；
- 商业航天融资必须同时命中至少一个主体锚点和至少一个融资事件锚点；
- 候选缺少非空标题或有效 HTTP(S) 链接时直接丢弃；
- 明确命中以下噪声主题时直接丢弃：
  - 激光打印机、打印耗材、硒鼓、墨盒；
  - 激光雕刻、激光切割、打标机；
  - 激光美容、脱毛、祛斑、医美；
  - 与四个板块无关的通用医疗器械或医疗防护用品；
  - 与四个板块无关的通用 AI 算法、算力、模型或软件采购。

过滤必须保守：只有明确命中噪声主题才排除，不使用宽泛的单字或容易误伤的否定词。

### FR-4：时间分桶与补足规则

通过相关性门槛的候选按来源发布日期分为：

- A 桶：最近 0–7 天；
- B 桶：最近 8–30 天；
- C 桶：来源发布日期缺失，但主题相关性门槛通过；
- 丢弃：超过 30 天或日期异常。

最终候选按以下顺序组成：

1. 先选 A 桶；
2. A 桶不足 5 条时，从 B 桶按日期由近到远补足；
3. 仍不足 5 条时，从 C 桶补充，但 C 桶最多展示 2 条；
4. 最终最多展示 10 条；
5. 同一 URL 继续使用现有规范化 URL 规则去重。

时间补足只解决“有无信息”，不得把 8–30 天或日期未知的候选描述为“过去 24 小时新增”。

### FR-5：候选排序

同一时间桶内按以下优先级排序：

1. 来源发布日期较新；
2. 官方或原始来源优先；
3. 标题和摘要同时命中主题锚点的候选优先；
4. URL 作为最终稳定排序键，保证相同输入得到相同输出。

本阶段不引入新的付费重排 API。

### FR-6：正文抓取失败时的展示

候选通过相关性与时间门槛后，无论正文是否抓取成功，报告都必须保留：

- 所属板块；
- 来源发布日期，或“发布日期未知”；
- 标题；
- 搜索摘要，并标注“未核实”；
- 原始来源链接；
- 正文抓取或核验失败原因。

只有完成现有核验要求的内容可以写入“已核实信息”。候选摘要不得伪装成已核实事实。

### FR-7：采集漏斗

报告和 Artifact 至少记录：

- `raw_search_count`：博查原始返回数量；
- `valid_shape_count`：标题和链接结构有效的数量；
- `relevance_pass_count`：通过相关性门槛的数量；
- `recent_7d_count`：A 桶数量；
- `fallback_8_30d_count`：实际采用的 B 桶数量；
- `unknown_date_count`：实际采用的 C 桶数量；
- `final_candidate_count`：去重后最终候选数量；
- `verified_count`：已核实数量；
- `pending_count`：未核实数量；
- `fetch_failure_count`：正文抓取失败数量；
- `failed_domains`：失败域名列表；
- 博查调用次数及查询覆盖情况。

指标命名可按现有模型风格调整，但含义不得缺失。

### FR-8：业务成功判定

Actions 进程退出成功不等于业务成功。

本阶段一次采集只有同时满足以下条件，才算“信息可用”：

- 4 个核心分类查询均已尝试；
- 博查响应可以解析；
- `final_candidate_count >= 5`；
- 每条最终候选都有标题、摘要和链接；
- 明显噪声样本数量为 0。

不足 5 条时，命令可以安全完成并生成 Artifact，但报告必须醒目标注“信息不足”，列出采集漏斗和原因，不能写成“暂无已核实信息”后掩盖失败。

## 8. 报告要求

报告中的候选展示格式应简洁：

```text
- [板块] 2026-07-27｜候选标题｜未核实：正文抓取失败｜原始链接
  - 搜索摘要（未核实）：……
```

日期未知时：

```text
- [板块] 发布日期未知｜候选标题｜未核实：来源日期缺失｜原始链接
```

报告必须区分：

- 近 7 天候选；
- 8–30 天补充候选；
- 发布日期未知候选；
- 已核实信息；
- 未核实信息。

## 9. 错误处理

- 博查网络错误、鉴权错误、限额错误、业务错误码和响应结构错误继续使用受控错误类型；
- 单个查询失败不得阻止其他查询执行；
- 单条候选结构异常不得丢弃同一响应中的其他候选；
- 单个网页抓取失败不得丢弃其搜索摘要；
- TLS 证书失败必须如实记录，不得关闭证书校验；
- 过滤器异常应使本次业务判定失败，不得默认放行全部候选；
- 日期解析失败应进入“日期未知”路径并计数，不得改写为当天日期。

### 10.2 固定样本验收

固定样本至少包含：

- 6 条近 7 天相关候选；
- 3 条 8–30 天相关候选；
- 3 条日期未知但相关候选；
- 2 条超过 30 天旧闻；
- 激光打印机、激光美容、激光雕刻、医疗用品、通用 AI 各 1 条噪声；

- 优先得到近 7 天候选；
- 噪声和超过 30 天旧闻不进入最终列表；
- 正文抓取失败的相关候选仍显示标题、摘要和链接；
- 所有漏斗计数与样本相符。

## 12. 风险与缓解

### 12.1 候选不足 5 条

缓解：先用 8–30 天候选补足，再允许最多 2 条日期未知但高度相关的候选；报告必须标明其时间状态。

### 12.2 关键词过滤误伤

缓解：采用明确短语和双锚点，不用宽泛单字；固定正反样本测试覆盖。

### 12.3 博查时效参数行为与预期不一致

缓解：真实 dry-run 检查返回日期分布；本地仍以 `datePublished` 执行最终时间门槛，不完全依赖 API。

### 12.4 原网页继续无法访问

缓解：把搜索摘要作为未核实候选交付，不让正文抓取失败再次造成空日报；不降低 TLS 安全要求。

### 12.5 Actions 显示成功但业务不足

缓解：独立输出采集漏斗与业务成功判定，报告明确提示“信息不足”。
