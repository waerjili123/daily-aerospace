# 分类证据合并与独立来源定向核验设计

日期：2026-07-29  
状态：已确认方案，待实现

## 1. 背景

GitHub Actions 运行 #16 验证了双通道核验机制已经生效：

- 基础搜索调用 12 次；
- 弹性核验调用 3 次；
- 总调用 15 次，没有超过硬上限；
- 定向核验处理 1 个事件，新增来源 1 个，重复来源 29 个；
- 最终候选 4 条、待核实 3 条、严格已核实 0 条。

本轮目标对象来自 `pedaily.cn`，核验原因是
`classification_evidence_invalid`。页面实际分别包含商业航天业务描述和融资
动作描述，但现有核验器隐含要求单条 `in_scope` 引文同时包含类别信号和事件
信号。真实新闻经常用不同句子陈述“公司从事什么业务”和“公司完成了什么融
资”，因此被误判为分类证据无效。

同时，定向核验查询没有排除目标页面自身域名。目标来自 `pedaily.cn` 时，系统
仍会执行 `site:pedaily.cn` 查询，造成大量重复结果，并占用本应寻找另一独立
B 级来源的弹性预算。

## 2. 目标

1. 允许同一页面内的多条原文证据共同证明事件处于目标范围。
2. 继续要求类别和事件类型都具有可复核的页面原文证据。
3. 定向核验跳过目标自身域名，把有限预算用于真正独立的来源。
4. 保持严格来源门槛、日期门槛、主体一致性和融资关键字段要求不变。
5. 下一次真实 dry-run 的首要验收目标仍是至少产生 1 条严格
   `verified` 信息。

## 3. 非目标

- 不降低 A/B/C 来源等级规则。
- 不把博查摘要、搜索日期或模型推断单独作为严格核验事实。
- 不允许两个互相矛盾的页面片段合成有效分类。
- 不增加 15 次总调用硬上限。
- 不修改 Secrets、钉钉配置、定时任务、仓库可见性或 workflow 启停状态。
- 不在本设计中处理非阻断的 checkout `git exit 128` 或 Node.js 弃用警告。

## 4. 方案选择

采用方案 A：页面级证据集合核验，并跳过目标自身来源域名。

未采用的方案：

- 方案 B：让分析模型生成一条同时包含类别和事件的组合引文。该方式可能生成
  原页面不存在的拼接句，不适合作为严格证据。
- 方案 C：只调整搜索查询。它可以减少重复，但不能解决已存在的分类证据误判。

## 5. 分类证据规则

### 5.1 保留的前置一致性检查

核验器仍先用确定性规则分析目标页面，并要求以下结果与主分析结果一致：

- `in_china`
- `in_scope`
- `category`
- `event_type`

任何冲突仍返回 `classification_rule_disagreement`。

### 5.2 必需证据字段

分析结果仍必须包含：

- `in_china`
- `in_scope`
- `category`
- `event_type`

缺失任一字段仍返回 `classification_evidence_missing`。

### 5.3 页面级联合证明

类别和事件类型不再被要求出现在同一条 `in_scope` 引文中。核验器将同一页面内
下列字段的原文证据视为一个受约束的页面级证据集合：

- `in_scope`
- `category`
- `event_type`

该集合必须同时满足：

1. 至少一条引文能被确定性规则识别为分析结果中的 `category`；
2. 至少一条引文能被确定性规则识别为分析结果中的 `event_type`；
3. 页面级确定性分析与主分析的范围、类别和事件类型完全一致。

类别证据和事件证据可以来自不同句子，但必须来自同一个目标页面，不能跨页面
拼接分类结论。

### 5.4 不变的严格门槛

分类证据通过后，融资事件仍必须继续通过：

- 主体一致性；
- 发布日期和时间范围；
- 金额或轮次等关键字段完整性；
- 官方来源，或两个相互独立的 B 级来源；
- 多来源事实一致性和冲突检查。

因此，本修改只消除不合理的“同一句话”限制，不会让单一 B 级媒体直接升级为
严格已核实。

## 6. 独立来源查询规则

### 6.1 目标自身域名排除

生成融资定向查询时，从目标候选 URL 提取规范化注册域名。构造 B 级媒体
`site:` 查询时：

- 跳过与目标候选相同的域名；
- 保留官网/投资机构官方披露查询；
- 按配置顺序使用剩余独立 B 级媒体域名；
- 总查询数仍受弹性预算 3 次限制。

例如，目标来自 `pedaily.cn` 时，三次查询优先为：

1. 企业官网或投资机构官方披露；
2. `site:stcn.com` 的同事件查询；
3. `site:cls.cn` 的同事件查询。

不再执行 `site:pedaily.cn` 的同源重复查询。

### 6.2 查询去重

现有的运行内查询去重和待核实状态中的历史查询去重继续生效。规范化后相同的
查询不得再次消耗弹性预算。

## 7. 数据流

1. 基础发现通道产生候选并完成首次抓取、分析和严格核验。
2. 对 `classification_evidence_invalid` 等允许追查的待核实对象进行排序。
3. 定向查询规划器提取目标自身域名并排除同域 B 级查询。
4. 新来源进入与基础候选相同的抓取、分析、事件合并和严格核验流程。
5. 每个页面先完成页面级分类证据核验，再执行多来源独立性和字段一致性核验。
6. 报告继续输出基础调用、弹性调用、新增来源、重复来源和最终核验状态。

## 8. 错误处理

- URL 无法解析域名时，不推断目标域名，但仍保留查询去重和总预算限制。
- 排除自身域名后没有剩余 B 级媒体时，只执行可用的官方查询，不用同源查询填满
  预算。
- 页面级证据集合只有类别证据或只有事件证据时，仍返回
  `classification_evidence_invalid`。
- 任一来源正文抓取或分析失败时，保持降级记录，不把搜索摘要提升为严格证据。

## 9. 测试设计

### 9.1 核验器测试

- 类别和融资动作分处两条原文引文，但来自同一页面且规则一致：分类证据通过。
- 只有商业航天类别证据，没有融资动作证据：仍为
  `classification_evidence_invalid`。
- 只有融资动作证据，没有商业航天类别证据：仍为
  `classification_evidence_invalid`。
- 页面规则分类与模型分类冲突：仍为 `classification_rule_disagreement`。
- 分类通过但只有一个 B 级来源：仍不能严格核实。
- 分类通过且存在两个独立 B 级一致来源：允许按现有规则严格核实。

### 9.2 查询规划器测试

- 目标来自 `pedaily.cn`：生成查询不包含 `site:pedaily.cn`。
- 目标来自 `stcn.com`：生成查询不包含 `site:stcn.com`。
- 目标来自非 B 级域名：仍可按配置生成三个 B 级查询，但受总预算限制。
- 域名大小写、`www` 和子域名正确归一化。
- 排除自身域名后查询数不足 3 时，不生成重复查询补位。

### 9.3 流水线测试

- 首次分类证据通过后，新增独立 B 级来源能参与再次核验。
- 基础 12 次加弹性调用始终不超过 15 次。
- 报告准确记录新增来源和重复来源数量。

### 9.4 完整回归

- 执行完整离线测试。
- 执行 `git diff --check`。
- 推送当前开发分支。
- 仅手动执行强制 dry-run 的 workflow。
- 核对业务摘要和 artifact，而非只依据 Actions 成功状态。

## 10. 验收标准

实现验收：

- 新增测试全部通过；
- 既有测试无回归；
- 目标自身域名不再消耗 B 级定向查询预算；
- 分类证据跨句但同页完整时不再误判。

真实运行验收：

- 基础调用不超过 12；
- 弹性调用仅在存在合格待核实对象时发生，且不超过 3；
- 总调用不超过 15；
- 目标是至少产生 1 条严格 `verified` 信息；
- 如仍为 0，报告必须明确剩余阻断是独立来源不足、字段冲突、日期问题或其他具
  体原因，不能仅以 Actions 成功代替业务成功。
