## 1. 交接目的

本文档用于把当前项目交给一个全新的 Codex 对话。新对话应以仓库、GitHub API、Actions 记录和产物为准，不应继续相信旧对话中未经验证的口头结论。

- 只采集中国境内公开信息。
- 招标板块覆盖激光通信、激光武器/激光反无人机、光电转塔/转台/吊舱。

- “AI日报”只曾作为结构参考；本仓库不得包含 AI 新闻日报内容。

第一次正式 `dry_run` 的报告为空，并显示“博查 API 返回格式异常”。旧对话一度错误地把 Actions 成功表述为“博查和 DeepSeek 链路成功”；这个说法是错的。真实情况是：

- GitHub Actions 进程退出成功。
- 博查请求返回了 HTTP 200。
- 现有解析器未找到结果，因此所有候选为 0。
- 没有候选时，DeepSeek 没有得到有效的真实数据验收。
- “运行成功”不等于“采集成功”。

随后建立了隔离诊断分支：

```text
codex/bocha-response-diagnostic
```

诊断提交：

- `f685cc8`：增加单请求脱敏诊断
- `9f86dab`：Actions 自动提交脱敏响应结构

诊断 Actions：

```text
https://github.com/waerjili123/daily-aerospace/actions/runs/30081624362
```

真实脱敏结果：

```json
{
  "http_status": 200,
  "business_code": 200,
  "root_keys": ["code", "data", "log_id", "msg"],
  "data_keys": ["_type", "images", "queryContext", "videos", "webPages"],
  "web_pages_path": "data.webPages",
  "results_type": "array",
  "result_count": 3
}
```

确定根因：

```text
博查真实结果位于 data.webPages.value
现有 main 只读取 webPages.value
```

诊断分支不应合并到 `main`。它只用于一次性验证响应结构。

- `schedule` 事件不会自动加 `--dry-run`。
- `Run daily pipeline` 成功意味着 CLI 没有报告钉钉发送失败。
- 因此这两次定时任务很可能各向钉钉发送了一条空日报。
- 这一点没有通过钉钉群截图再次核验，应让用户确认群内实际消息。

另一个异常：

- 工作流文件写的是 `cron: "30 23 * * *"`，设计意图是北京时间 07:30。
- 两次实际 `created_at` 分别为 UTC 07:30 和 07:57，即北京时间约 15:30 和 15:57。
- 不要假设调度已经正确；新对话需要调查 GitHub 实际触发时间和延迟原因。

建议新对话第一优先级处理：

1. 询问用户是否先暂停/禁用定时 workflow，避免继续消耗博查额度和发送空消息。
2. 未经用户授权不要直接禁用或修改。
3. 在修复和业务验收完成前，建议所有手动测试保持 `dry_run=true`。

## 12. 推荐的新对话执行顺序

新对话应先只读核对，不要立刻合并或运行：

1. 阅读本文档和 `docs/PROGRESS.md`。
2. `git fetch origin`，确认 `origin/main`、PR #3 和分支状态。
3. 通过 GitHub API/页面再次确认是否出现新的 scheduled run。
4. 向用户报告“定时任务可能仍在继续发送空日报”，询问是否暂停 workflow。
5. 向用户报告仓库是 public，询问是否改 private。
6. 复核 PR #3 代码和测试，不要合并诊断分支。
7. 用户授权后，把 PR #3 更新到最新 `main` 并合并。
8. 临时把测试查询数降到很小，或增加显式单次验收模式，避免一次消耗约 15 次搜索。
9. 手动运行 `dry_run=true`。
10. 下载并审核 Artifact，至少确认：
    - 博查不再报格式异常。
    - 候选数大于 0。
    - DeepSeek 确实被调用或明确降级。
    - 有可点击原始链接。
    - `pending` 与正式项目的验证规则符合设计。
    - 日报不是把“无法核验”误写成“没有信息”。
11. 调查官方来源在 GitHub runner 上全部失败的问题。
12. 修正并验证北京时间 07:30 调度。
13. 只有 Artifact 人工审核通过后，才运行一次 `dry_run=false` 验收钉钉。
